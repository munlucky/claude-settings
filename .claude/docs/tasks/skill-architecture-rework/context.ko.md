# 스킬 아키텍처 재정비 컨텍스트

Last-Reviewed: 2026-03-27

## 목표

로컬 스킬과 에이전트를 전면 교체하지 않고, 안전하게 재구성하기 위한 구현 직전 준비 워크플로우를 정의한다.

이 작업은 아래 경로의 소스 수정 직전에서 멈춘다.
- `.claude/skills/**`
- `.claude/agents/**`
- `.claude/rules/**`
- 실행 라우팅 스크립트

## 작업 가설

현재 저장소는 리셋이 아니라 재배치가 필요하다.

핵심은 다음이다.
- 공개 진입점 모델 명확화
- 오케스트레이터, 번들, 마이크로스킬, 어댑터 경계 정리
- `유지 / 병합 / 폐기 후보 / 개선` 판단 절차 표준화

현재 기준 가설:
- `product-orchestrator`는 제품 정의 진입점
- `moonshot-phase-runner`는 대형 phase 기반 작업의 기본 진입점
- `moonshot-orchestrator`는 범위가 정해진 구현 진입점

## 이 문서가 필요한 이유

최근 분석에서 다음이 확인됐다.
- 현재 repo는 강한 워크플로우 자산을 이미 갖고 있어 무작정 교체하면 손해다
- Moonshot 분석, 실행, 리뷰, 문서화 계층에 책임 중복이 있다
- 공개 진입점과 내부 실행 부품의 경계가 한곳에 정리돼 있지 않다
- 번들 메타데이터와 실제 파일 사이에 드리프트가 있다
  - 예: `code-simplifier`가 번들에는 있으나 `.claude/skills/`에는 없음

## 범위 포함

- 현재 스킬, 에이전트, 게이트, 번들, 실행 어댑터 인벤토리 작성
- tier 모델과 책임 경계 정의
- 각 자산을 `유지`, `병합 후보`, `폐기 후보`, `개선`으로 분류
- 런타임 동작 수정 전에 필요한 선행 조건 문서화
- 이후 구현 작업을 위한 컷오버 계획 준비

## 범위 제외

- 스킬 동작 수정
- 스킬/에이전트 이름 변경
- 파일 삭제
- 셸/런타임 디스패치 변경
- 설치 동작 변경
- 검증 strictness 기본값 변경

## 제약 조건

- 도메인 가치가 있는 repo 고유 자산은 보존한다
- 준비 단계에서는 외부 스킬을 기본값으로 들이지 않는다
- 단일 책임이 분명한 마이크로스킬은 유지한다
- 내부 부품 단순화보다 공개 호출 표면 단순화를 우선한다
- 병합 결정은 현재 실행 의미를 보존하거나, 의미 변경을 명시해야 한다

## 필수 산출물

구현 시작 전까지 아래 산출물이 있어야 한다.
- 이 컨텍스트 문서
- 단계별 준비 명세
- 현재 자산을 덮는 인벤토리 매트릭스
- 명시적인 `Ready For Change` 게이트

## 초기 Tier 가설

### Tier 1: 공개 진입점

- `product-orchestrator`
- `moonshot-phase-runner`
- `moonshot-orchestrator`

### Tier 2: 조합/제어 계층

- workflow bundle
- teams runner
- phase executor
- coordinator 계열

### Tier 3: 마이크로스킬

- gate
- analyzer
- reviewer
- runner
- 문서 운영 계열

### Tier 4: 내부 어댑터

- shell script
- runtime bridge script
- execution dispatch wrapper

## Ready For Change

아래 조건이 모두 참일 때만 구현 작업을 시작한다.

1. 현재 스킬과 에이전트가 모두 분류돼 있다.
2. 공개 진입점마다 역할과 제외 경계가 선언돼 있다.
3. 병합 후보마다 롤백 가능한 migration note가 있다.
4. 폐기 후보마다 대체 경로 또는 사실상 미사용이라는 판단 근거가 있다.
5. bundle 정의와 실제 파일 구성이 일치한다.
6. 대형 작업 진입 경로에 대한 모호함이 남아 있지 않다.

하나라도 거짓이면 문서화 단계에서 멈추고 런타임 자산을 수정하지 않는다.
