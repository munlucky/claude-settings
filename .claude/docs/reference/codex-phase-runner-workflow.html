1. 핵심 요약

페이즈러너는 “큰 프롬프트 하나”가 아니라 파일 시스템 산출물로 상태를 유지하는 실행 장치입니다. Codex worker가 완료를 주장해도 끝이 아니며, QA_REPORT.md, SCORECARD.md, verification verdict, lease gate가 완료 여부를 판단합니다.

  • 큰 작업은 moonshot-phase-runner로 들어가고, bounded 작업은 moonshot-orchestrator, 제품 정의는 product-orchestrator가 맡습니다.
  • 단계는 Intake → Plan → Ready / Isolate → Execute → Review → Verify → Finish / Handoff 순서입니다.
  • phase verdict는 기존 done / retry / blocked를 유지합니다.
  • task-level status는 FULL / PARTIAL / NO를 추가로 사용합니다.
  • clean finish에는 Verdict: done과 Current task status: FULL이 모두 필요합니다.
  • strict/phase 작업에서는 branch/worktree뿐 아니라 ignored agent config hydration과 baseline evidence도 Ready / Isolate 조건입니다.

2. 사용자 관점 Flow

처음 보는 개발자는 이 순서로 이해하면 됩니다. 사용자는 Codex 채팅창에 요청을 입력하지만, 실제 실행 상태는 채팅이 아니라 repository의 파일과 스크립트로 이어집니다.

Codex chat session
  -> user asks for phase-based execution
  -> Codex selects moonshot-phase-runner skill
  -> runner reads workspace contract and plan documents
  -> runner creates/updates phase-status.yaml
  -> runner seeds SPRINT/QA/HANDOFF/SCORECARD files
  -> executor starts dispatcher script
  -> dispatcher starts delegated worker loop
  -> worker receives one-phase prompt
  -> worker edits code and artifact files
  -> completion gate reads evidence files
  -> retry, next phase, or final return

  -> in_progress
  -> ready/isolate checked
  -> execute attempted
  -> review recorded
  -> verification recorded
  -> scorecard evaluated
  -> completed
retry      # 같은 phase를 다시 시도한다. 단, 같은 failure class 반복 시 tactic을 바꾼다.
blocked    # 환경, 계약, 의존성, 설계 문제로 더 진행할 수 없다.
PARTIAL    # 핵심 흐름은 유지되지만 acceptance/coverage가 남았다.
NO         # hard gate 실패, critical regression, blocking defect 등으로 완료 불가다.

현재 어디까지 왔는지 확인하는 순서

1. phase-status

.claude/docs/phase-status.yaml에서 active plan directory와 phase 상태를 확인합니다.

2. sprint contract

SPRINT_CONTRACT.md에서 worker가 해야 할 exact files, commands, expected signals를 확인합니다.

3. QA report

QA_REPORT.md에서 현재 stage, TDD evidence, failure cause, review, verification evidence를 확인합니다.

4. scorecard

SCORECARD.md에서 Verdict: done, Current task status: FULL, unmet 0, blocking 0 여부를 확인합니다.

5. handoff

HANDOFF.md에서 clean finish가 아닌 경우 멈춘 이유와 다음 시도 지시를 확인합니다.

Successphase 완료 후 다음 phase로 넘어가거나 최종 요약이 나옵니다.SCORECARD.md has Verdict: done and Current task status: FULL.next phase or final return

처음 보는 사람이 자주 헷갈리는 부분

  • Codex가 완료했다고 말해도 완료가 아닙니다. SCORECARD.md와 verdict JSON이 완료 조건입니다.
  • 테스트를 실행했다는 말만으로는 evidence가 아닙니다. command, exit code, artifact path, freshness가 함께 있어야 합니다.
  • Phase 1 완료는 전체 작업 완료가 아닙니다. actionable phase가 남아 있으면 final response boundary가 아닙니다.
  • worktree가 있다는 것만으로 Ready / Isolate 통과가 아닙니다. ignored agent config hydration과 baseline evidence가 필요할 수 있습니다.
  • 다시 시도했다는 것만으로 충분하지 않습니다. 같은 failure class가 반복되면 next tactic이 달라져야 합니다.

Step 1. Codex 채팅 세션에서 요청이 들어온다

사용자가 보는 것docs/implementation phase plan을 끝까지 실행해줘.
AI 컨텍스트workspace root, user request, available skills, AGENTS.md, .claude/CLAUDE.md, verification contract.
실제 실행아직 script는 실행하지 않고, 요청이 bounded/product/phase 작업인지 판단합니다.
다음 조건large/phase/long-running 구현이면 moonshot-phase-runner를 선택합니다.

Step 2. moonshot-phase-runner skill이 선택된다

사용자가 보는 것Codex가 phase runner로 진행한다는 짧은 진행 업데이트를 낼 수 있습니다.
AI 컨텍스트.claude/skills/moonshot-phase-runner/SKILL.md, .claude/docs/guidelines/skill-composition.md, workspace contract.
실제 실행worker는 아직 시작하지 않고, runner가 plan directory를 찾을 준비를 합니다.
다음 조건명시된 plan dir이 있으면 우선 사용하고, 없으면 active status 또는 docs/implementation/을 찾습니다.

Step 3. Runner가 plan과 workspace contract를 읽는다

읽는 파일.claude/CLAUDE.md, .claude/verification.contract.yaml, .claude/docs/phase-status.yaml, docs/implementation/00-master-plan*.md, docs/implementation/<NN>-*.md.
AI 판단이미 진행 중인지, phase가 몇 개인지, Q&A가 필요한지, autonomous 실행인지 판단합니다.
실제 실행plan directory resolution을 수행하고, 안전한 plan이 없으면 moonshot-plan-writer로 plan 생성을 유도합니다.
다음 조건후보가 여러 개면 추측하지 않고 사용자 확인이 필요합니다.

Step 4. phase-status.yaml과 execution package가 만들어진다

생성/수정 파일.claude/docs/phase-status.yaml, SPRINT_CONTRACT.md, QA_REPORT.md, HANDOFF.md, SCORECARD.md.
AI 컨텍스트phase number/title/status, execution mode, active stage, artifact path mapping, stage order.
실제 실행 파일agent-loop-phase-artifacts.mjs, .claude/templates/execution/*.
다음 조건--prepare-only면 준비 결과만 반환하고, 기본값이면 dispatcher로 넘어갑니다.

Step 5. Executor가 dispatcher command를 만든다

  "executionMode": "delegated-terminal",  // 기본 장기 실행 모드
  "runtime": "codex",                     // active runtime

실제 실행node .claude/scripts/moonshot-phase-dispatch.mjs docs/implementation --runtime codex
생성 파일active-phase-run.json, current-run.json, .claude/logs/agent-loop/
핵심 의미lease가 시작되면 “아직 최종 응답하면 안 된다”는 반환 경계가 생깁니다.
다음 조건dispatcher가 lease를 잡으면 agent loop가 시작됩니다.

Step 6. Agent loop가 다음 phase 하나를 고른다

AI 컨텍스트active lease id, target runtime, retry cap, next actionable phase, artifact path.
실제 실행agent-loop.mjs가 다음 phase를 고르고, agent-loop-phase-runner.mjs --single-phase가 한 phase를 실행합니다.
읽는 파일phase-status.yaml, phase doc, SPRINT, QA, HANDOFF, SCORECARD.
다음 조건worker에게는 phase 하나만 넘기고, 다른 phase scope는 섞지 않습니다.

Step 7. Worker prompt가 만들어지고 Codex worker가 실행된다

이번 시도에서는 Phase 1만 수행한다.
moonshot-phase-runner를 다시 호출하지 마라.
phase doc과 SPRINT_CONTRACT.md를 먼저 읽어라.
Ready / Isolate -> Execute -> Review -> Verify -> Finish / Handoff 순서를 유지하라.
행동 변경이면 production code 전에 failing test를 작성하라.
fresh verification evidence 없이 완료를 주장하지 마라.
완료하려면 SCORECARD.md가 Verdict: done과 Current task status: FULL이어야 한다.
runtime commandcodex exec --full-auto -C <workspace>
전달 경로phaseDoc, sprintContract, qaReport, handoff, scorecard.
생성/수정WORKSET.md, QA_REPORT.md, SCORECARD.md attempt checkpoint.
다음 조건worker는 artifact를 먼저 읽고 checkpoint를 남긴 뒤 구현합니다.

Step 8. Ready / Isolate evidence가 확인된다

왜 필요한가작업 프로젝트에서는 .claude, .agents, .codex가 ignored일 수 있어 worktree에 agent harness가 빠질 수 있습니다.
실행 commandbash .claude/scripts/harness-prepare-worktree.sh TASK-001 --hydrate-agent-config --baseline-command "npm test"
생성 evidence<worktree>/.claude/worktree-prepare.json, baseline log, hydrated .claude/.agents/.codex.
다음 조건strict/phase 작업에서 evidence가 없거나 baseline이 실패하면 implementation으로 들어가지 않습니다.

Step 9. Worker가 구현과 테스트를 수행한다

AI 컨텍스트SPRINT_CONTRACT.md의 exact files, exact commands, expected signals, blockers, TDD rule.
실행 예pytest tests/test_feature.py -v, npm test, node --test, npm run build.
수정 파일product source, tests, QA_REPORT.md, SCORECARD.md, 필요 시 HANDOFF.md.
다음 조건구현이 끝나도 review와 verification이 남아 있으므로 완료 선언은 아직 금지됩니다.

Step 10. Review와 verification evidence가 생성된다

Review 컨텍스트code-changing work인지, review owner, findings, accepted/challenged/deferred decision.
Verification 컨텍스트.claude/verification.contract.yaml, required checks, fresh evidence rule.
생성 파일.claude/verification-verdict-*.json, .claude/runtime-verdict-*.json, updated QA_REPORT.md.
다음 조건fresh하고 relevant한 evidence가 있으면 scorecard를 갱신하고, 실패하면 failure class와 root cause를 기록합니다.

Step 11. Completion gate가 done + FULL을 판정한다

읽는 파일QA_REPORT.md, SCORECARD.md, HANDOFF.md, verification/runtime verdict JSON.
실제 평가agent-loop-phase-state.mjs가 score, unmet, blocking, review, verification, task status를 평가합니다.
통과 조건fresh evidence, review evidence, target score, unmet 0, blocking 0, Verdict: done, Current task status: FULL.
실패 시retry, PARTIAL, NO, blocked 이유를 기록하고 loop로 돌아갑니다.

Step 12. 다음 phase로 넘어가거나 최종 반환한다

Phase 1 done + FULL
  -> Phase 2 pending? yes
  -> return to agent-loop
  -> build Phase 2 one-phase prompt
최종 확인 commandnode .claude/scripts/phase-run-lease.mjs assert-return-allowed <status-file> <runLeaseId> true false
반환 허용 조건actionable phase 없음, active lease 유효, 마지막 phase clean finish, valid stop reason.
사용자 최종 응답완료 phase 요약, verification evidence, scorecard status, handoff가 있으면 이유.
핵심 규칙단일 phase 완료만으로는 final response가 허용되지 않습니다.

6. 7단계 Stage Model

1. Intake요청 유형과 workflow profile을 판별합니다.
2. Plan파일, 명령, 기대 신호, blocker가 있는 계획을 만듭니다.
3. Ready / Isolatebranch/worktree, hydration, baseline evidence를 확인합니다.
4. ExecuteTDD-first와 implementation runner가 phase 범위 안에서 실행합니다.
5. Reviewcode review와 security review evidence를 기록합니다.
6. Verifyfresh verification verdict와 evidence path를 남깁니다.
7. Finish / Handoffdone + FULL 또는 valid stop handoff를 기록합니다.

medium, complex, phase 작업은 이 단계가 보이게 남아야 합니다. 작은 bounded 작업은 압축할 수 있지만, 검증 evidence와 unsupported completion claim 방지는 생략하지 않습니다.

12. 산출물 계약

SPRINT_CONTRACT.md

  • policy anchor
  • exact files to create/modify/test
  • exact commands
  • expected fail/pass signal
  • blocker condition
  • TDD contract
  • workspace isolation evidence

QA_REPORT.md

  • attempt start/current stage
  • red/green/refactor evidence
  • failure class/root cause/next tactic
  • review evidence
  • verification command/exit code/verdict path
  • next path

HANDOFF.md

  • valid stop reason
  • remaining work
  • rerun commands
  • required next-attempt reads
  • why the run stopped

SCORECARD.md

  • phase verdict: done/retry/blocked
  • score/target
  • unmet checklist count
  • blocking defect count
  • task-level status: FULL/PARTIAL/NO

Scorecard 예시

## Phase Verdict

- Verdict: done                         # phase verdict
- Score: 95 / 100                       # objective weighted score
- Target: 90                            # pass target
- Unmet checklist items: 0              # clean finish requires zero
- Blocking defects: 0                   # clean finish requires zero

## Task-Level Status Adapter

- Current task status: FULL             # FULL, PARTIAL, or NO
- fail-to-pass signal: satisfied        # acceptance checks now pass
- pass-to-pass signal: preserved        # regression checks remain preserved
- Required verification evidence: present # evidence is present and referenced
- Status reason: target met with no unmet checklist or blocking defects

13. 완료 게이트

구현 command가 exit 0이어도 phase는 완료되지 않습니다. clean finish는 다음 조건을 모두 봅니다.

  • QA_REPORT.md가 verifier pass와 fresh evidence를 기록합니다.
  • 참조된 verification/runtime verdict JSON이 현재 phase와 관련 있고 fresh합니다.
  • .claude/verification.contract.yaml의 required checks가 존재합니다.
  • 코드 변경이 있으면 codex-review-code 또는 명시적 review evidence가 있습니다.
  • SCORECARD.md가 target 이상, unmet 0, blocking 0, Verdict: done입니다.
  • SCORECARD.md가 Current task status: FULL입니다.
  • finish-closeout과 handoff가 placeholder 형태로 남아 있지 않습니다.

PARTIAL 또는 NO는 completion gate에서 차단됩니다. legacy scorecard는 done + target 충족 + unmet 0 + blocking 0이면 FULL로 추론할 수 있지만, 새 scorecard는 명시적으로 Current task status: FULL을 남겨야 합니다.

14. 실패 루프

16. 반환 경계

성공 반환 경계는 단일 phase가 아니라 active plan directory 전체입니다.

node .claude/scripts/phase-run-lease.mjs assert-return-allowed <status-file> <runLeaseId> true false

반환 허용

  • 모든 actionable phase가 완료됨
  • 현재 phase가 Verdict: done + Current task status: FULL
  • active lease가 유효함
  • 검증, review, finish evidence가 일관됨

반환 차단

  • actionable phase가 남아 있음
  • lease가 없거나 stale임
  • scorecard가 retry, blocked, PARTIAL, NO임
  • 검증 완료만 있고 review/finish closeout이 없음
  • checkpoint artifact refresh를 완료로 오인함

최종 mental model: user request -> public entrypoint -> 7-stage workflow -> plan docs -> phase-status.yaml -> execution artifacts -> isolated worker attempt -> evidence -> done + FULL -> lease-approved final return.
