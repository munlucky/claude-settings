1. 핵심 요약

페이즈러너는 “큰 프롬프트 하나”가 아니라 파일 시스템 산출물로 상태를 유지하는 실행 장치입니다. Codex worker가 완료를 주장해도 끝이 아니며, QA_REPORT.md, SCORECARD.md, verification verdict, lease gate가 완료 여부를 판단합니다.

  • 큰 작업은 moonshot-phase-runner로 들어가고, bounded 작업은 moonshot-orchestrator, 제품 정의는 product-orchestrator가 맡습니다.
  • 단계는 Intake → Plan → Ready / Isolate → Execute → Review → Verify → Finish / Handoff 순서입니다.
  • phase verdict는 기존 done / retry / blocked를 유지합니다.
  • task-level status는 FULL / PARTIAL / NO를 추가로 사용합니다.
  • clean finish에는 Verdict: done과 Current task status: FULL이 모두 필요합니다.
  • strict/phase 작업에서는 branch/worktree뿐 아니라 ignored agent config hydration과 baseline evidence도 Ready / Isolate 조건입니다.

5. 7단계 Stage Model

1. Intake요청 유형과 workflow profile을 판별합니다.
2. Plan파일, 명령, 기대 신호, blocker가 있는 계획을 만듭니다.
3. Ready / Isolatebranch/worktree, hydration, baseline evidence를 확인합니다.
4. ExecuteTDD-first와 implementation runner가 phase 범위 안에서 실행합니다.
5. Reviewcode review와 security review evidence를 기록합니다.
6. Verifyfresh verification verdict와 evidence path를 남깁니다.
7. Finish / Handoffdone + FULL 또는 valid stop handoff를 기록합니다.

medium, complex, phase 작업은 이 단계가 보이게 남아야 합니다. 작은 bounded 작업은 압축할 수 있지만, 검증 evidence와 unsupported completion claim 방지는 생략하지 않습니다.

6. 전체 실행 흐름

User

  -> moonshot-phase-runner

  -> master/phase validation
  -> phase-status.yaml
  -> execution artifact seeding
  -> moonshot-phase-executor
  -> moonshot-phase-dispatch.mjs
  -> phase-run lease start
  -> agent-loop.mjs
  -> agent-loop-phase-runner.mjs
  -> Ready / Isolate gate
  -> Codex or Claude worker attempt
  -> TDD / implementation / review / verification

  -> final handoff summary

중요한 변화는 완료 조건입니다. 이전에는 Verdict: done 중심이었지만, 현재는 Verdict: done과 Current task status: FULL이 함께 필요합니다.

8. Worktree Hydration

실제 작업 프로젝트에서는 .claude, .agents, .codex가 .gitignore에 들어가는 경우가 많습니다. 그래서 git worktree add만으로는 agent 설정과 하네스가 따라가지 않습니다.

bash .claude/scripts/harness-prepare-worktree.sh TASK-001 \
  --hydrate-agent-config \
  --baseline-command "npm test"

복사 대상

  • .claude/CLAUDE.md, .claude/CLAUDE.ko.md
  • .claude/verification.contract.yaml
  • .claude/rules/, .claude/skills/, .claude/agents/
  • .claude/scripts/, .claude/templates/, .claude/docs/guidelines/
  • .agents/skills -> ../.claude/skills symlink 또는 copy fallback
  • AGENTS.md -> .claude/CLAUDE.md symlink 또는 copy fallback
  • .codex/는 인증 복사 없이 scaffold만 생성

제외 대상

  • .claude/logs, .claude/cache, .claude/memory.json
  • .claude/verification-verdict-*, .claude/runtime-verdict-*
  • .claude/knowledge-repo-audit-*
  • .codex/auth.json, session, cache, logs

10. 프롬프트 구조

Codex worker에게 전달되는 영어 프롬프트의 의미를 한글로 풀면 다음과 같습니다.

당신은 이 phase 하나만 수행하는 worker입니다.
moonshot-phase-runner를 다시 호출하지 마세요.
활성 phase 문서와 SPRINT_CONTRACT.md를 먼저 읽으세요.
Ready / Isolate -> Execute -> Review -> Verify -> Finish / Handoff 순서를 유지하세요.
행동 변경 작업이면 production code 전에 failing test를 먼저 작성하세요.
테스트가 불가능하면 이유와 대체 verification path를 QA_REPORT.md에 기록하세요.
계획을 먼저 비판적으로 읽고 blocker가 있으면 추측하지 말고 멈추세요.
동일 failure class가 두 번 반복되면 같은 tactic을 반복하지 마세요.
코드 변경이 있으면 codex-review-code 또는 동등한 review evidence를 남기세요.
fresh verification evidence 없이 완료를 주장하지 마세요.
SCORECARD.md는 Verdict: done 및 Current task status: FULL이어야 clean finish가 가능합니다.

11. 산출물 계약

SPRINT_CONTRACT.md

  • policy anchor
  • exact files to create/modify/test
  • exact commands
  • expected fail/pass signal
  • blocker condition
  • TDD contract
  • workspace isolation evidence

QA_REPORT.md

  • attempt start/current stage
  • red/green/refactor evidence
  • failure class/root cause/next tactic
  • review evidence
  • verification command/exit code/verdict path
  • next path

HANDOFF.md

  • valid stop reason
  • remaining work
  • rerun commands
  • required next-attempt reads
  • why the run stopped

SCORECARD.md

  • phase verdict: done/retry/blocked
  • score/target
  • unmet checklist count
  • blocking defect count
  • task-level status: FULL/PARTIAL/NO

Scorecard 예시

## Phase Verdict

- Verdict: done                         # phase verdict
- Score: 95 / 100                       # objective weighted score
- Target: 90                            # pass target
- Unmet checklist items: 0              # clean finish requires zero
- Blocking defects: 0                   # clean finish requires zero

## Task-Level Status Adapter

- Current task status: FULL             # FULL, PARTIAL, or NO
- fail-to-pass signal: satisfied        # acceptance checks now pass
- pass-to-pass signal: preserved        # regression checks remain preserved
- Required verification evidence: present # evidence is present and referenced
- Status reason: target met with no unmet checklist or blocking defects

12. 완료 게이트

구현 command가 exit 0이어도 phase는 완료되지 않습니다. clean finish는 다음 조건을 모두 봅니다.

  • QA_REPORT.md가 verifier pass와 fresh evidence를 기록합니다.
  • 참조된 verification/runtime verdict JSON이 현재 phase와 관련 있고 fresh합니다.
  • .claude/verification.contract.yaml의 required checks가 존재합니다.
  • 코드 변경이 있으면 codex-review-code 또는 명시적 review evidence가 있습니다.
  • SCORECARD.md가 target 이상, unmet 0, blocking 0, Verdict: done입니다.
  • SCORECARD.md가 Current task status: FULL입니다.
  • finish-closeout과 handoff가 placeholder 형태로 남아 있지 않습니다.

PARTIAL 또는 NO는 completion gate에서 차단됩니다. legacy scorecard는 done + target 충족 + unmet 0 + blocking 0이면 FULL로 추론할 수 있지만, 새 scorecard는 명시적으로 Current task status: FULL을 남겨야 합니다.

13. 실패 루프

실패 처리는 systematic debugging 규칙을 따릅니다. 원인 확인 전 수정 금지, 동일 failure class 2회 반복 시 tactic 변경, 3회 실패 시 설계/계약 문제로 승격이 기본 원칙입니다.

{
  "failureClass": "verification_contract", // 반복 감지용 실패 분류
  "rootCauseEvidence": "QA_REPORT.md에 verdict path가 없음", // 실제 관측 증거
  "attemptedFixes": ["verdict 파일만 생성함"], // 이미 시도한 수정
  "sameFailureClassCount": 2,              // 같은 실패 분류 반복 횟수
  "nextTactic": "QA closeout artifact sync부터 수정" // 다음 시도 전략
}

15. 반환 경계

성공 반환 경계는 단일 phase가 아니라 active plan directory 전체입니다.

node .claude/scripts/phase-run-lease.mjs assert-return-allowed <status-file> <runLeaseId> true false

반환 허용

  • 모든 actionable phase가 완료됨
  • 현재 phase가 Verdict: done + Current task status: FULL
  • active lease가 유효함
  • 검증, review, finish evidence가 일관됨

반환 차단

  • actionable phase가 남아 있음
  • lease가 없거나 stale임
  • scorecard가 retry, blocked, PARTIAL, NO임
  • 검증 완료만 있고 review/finish closeout이 없음
  • checkpoint artifact refresh를 완료로 오인함

최종 mental model: user request -> public entrypoint -> 7-stage workflow -> plan docs -> phase-status.yaml -> execution artifacts -> isolated worker attempt -> evidence -> done + FULL -> lease-approved final return.
